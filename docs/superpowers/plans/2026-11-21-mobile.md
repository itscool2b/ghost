# Mobile: a real phone beside the chat, for you and your agents

Owner, 21 November 2026: "Create the greatest system of all time for mobile app development.
Obviously this app is on windows Mac and Linux", so Android and iPhone development "gonna be
different". "Figure out ALL logistics", then "make the ultimate plan that encompasses everything
then execute".

The goal: a person building a phone app in o7 sees the app running on a real device beside the
chat, on any of the three desktop systems, and every agent can build it, launch it, look at it,
use it and read its logs, so an agent can check its own work before it says it is done.

## What the references do (checked 21 November 2026)

- **Claude Code desktop**: an iOS Simulator pane beside the conversation, macOS only, local
  sessions only. It streams the screen, the person taps by clicking, the agent's taps act on the
  same device, a badge shows while the agent drives it, consent is asked once per device, and
  simulators it booted shut down 10 minutes after they are detached
  (code.claude.com/docs/en/desktop-ios-simulator).
- **Codex**: a Build iOS Apps plugin (June 2026) that mirrors the simulator in its in-app browser
  through XcodeBuildMCP. It needs a local Xcode.
- **Cursor**: no device pane (a staff reply on its forum).
- **Google**: the Android CLI (stable 1.0, May 2026) and Android skills, made for agents:
  projects, SDK setup, headless emulators, `android device hub` (a mirror window), and paid remote
  devices. It reports usage to Google unless `--no-metric` is passed.
- **Apple**: Xcode 26.3's `xcrun mcpbridge` gives outside agents builds, logs and SwiftUI
  previews, with Xcode open. Xcode 27 replaced Simulator.app with Device Hub and taught
  `devicectl` about simulators; tools that opened Simulator.app by name broke.
- **Expo**: Expo Go and development builds, EAS Build on Expo's Macs, and Expo Simulators (cloud
  iOS and Android simulators for agents, streamed to a browser, billed by the minute).
- **Open tools**: scrcpy (Android screen and input over adb, Apache-2.0), AXe and idb (iOS
  simulator input and accessibility, MIT), agent-device and mobile-mcp (agent CLIs over both
  systems), Maestro (flows).

Nobody ships Android in a pane, nobody ships either system on Windows or Linux, and every one of
them serves one agent. o7 does all three.

## What works where

| Computer | Android | iPhone |
| --- | --- | --- |
| Windows | Emulator and phones on a cable. The emulator needs Windows Hypervisor Platform. | No simulator: Apple ships it only for macOS. See "iPhone without a Mac". |
| Linux | Emulator and phones on a cable. The emulator needs KVM. | As Windows. |
| macOS | Emulator and phones on a cable. | The simulator, once the person has installed Xcode. |

### iPhone without a Mac

Offered in this order, and the pane says plainly which one a person is on:

1. **Their own iPhone with Expo Go** (Expo and React Native projects): the pane shows the dev
   server's QR code and its state; changes hot reload on the phone. Free. The phone's screen is
   not in the pane.
2. **A cloud simulator** on the person's own Expo account, streamed into the pane and driven by
   the same tools. Billed by Expo by the minute; o7 shows the meter and stops idle sessions.
3. **A Mac they own elsewhere**, reached over SSH: builds and the simulator run there, the pane
   shows it here. The largest piece; last.

For Expo, React Native, Flutter and Kotlin Multiplatform projects the Android emulator covers
most of the work on any computer, and the iPhone check is the last step, not every step.

## Decisions

1. **One feature, named Mobile.** A universal plugin beside Browser use (on by default, a switch,
   no Add or Remove) and a **Device** pane beside the chat. In code: `o7-devices` (the engine),
   `o7_core::mobile_service`, the helper mode `--o7-mobile-helper`, the tool server `o7_mobile`
   (id `o7-mobile`), tools named `mobile_*`. "Device" alone is taken in code
   (`o7_core::device`, this computer's identity) and in Settings (Remote access pairs devices).
2. **o7 owns the device layer.** It does not bundle an agent CLI. The pane, the per-chat device,
   the consent rules and the switch all need the device in o7's own hands, as the browser needed
   its own webviews. Agents remain free to use `adb`, `xcrun` or the Android CLI in their own
   shell; the tools here are what o7 answers for.
3. **Android speaks adb's own protocol.** A small async client talks to the adb server on
   127.0.0.1:5037 (`host:track-devices-l`, `host:transport:<serial>`, `shell:`, `exec:`,
   `sync:`), started with `adb start-server` when it is not running. No process per call.
4. **The screen is scrcpy's.** The pinned `scrcpy-server` (Apache-2.0, checked by SHA-256,
   bundled in the app) is pushed to the device and started in forward-tunnel mode; its sockets are
   opened through the adb transport (`localabstract:`), so no TCP port is forwarded or listened
   on. One path serves emulators and phones on a cable. Video is H.264; the pane decodes it with
   WebCodecs and draws to a canvas. Where the webview has no WebCodecs (some WebKitGTK builds) the
   pane shows still pictures taken on demand and after each action.
5. **Input is scrcpy's control channel**: touches, keys, text, Back, Home, the app switcher,
   rotation, the clipboard. The person's clicks and the agent's taps reach the same device.
6. **The emulator has no window of its own** (`-no-window`). o7 starts and stops it, keeps its
   AVDs in its own folder (`<data>/devices/android/avd`, via `ANDROID_AVD_HOME`) and never lists,
   starts or changes an AVD the person made in Android Studio.
7. **Setup without Java.** The pane needs three SDK packages: platform-tools, the emulator and one
   system image. o7 finds an SDK the person already has (`ANDROID_HOME`, `ANDROID_SDK_ROOT`, the
   default folders) and otherwise offers to fetch those packages itself from Google's repository
   index, each checked against the index's checksum, into `<data>/devices/android/sdk`. The
   person reads and accepts Google's SDK licence in the pane first; o7 never accepts it for them.
   AVD files are written directly (`config.ini`), so no `avdmanager`, no JDK. Building an Android
   project still needs the project's own JDK and build tools; the pane says what is missing and
   the agent's skill says how to install it.
8. **Reading the screen is an outline with refs**, as in the browser: `uiautomator dump` parsed to
   roles, names, states and a ref (`d12`) per element that can be acted on. A password field's
   text never appears in it.
9. **One device per chat.** A chat's worktree is its own copy of the project, so two chats on one
   emulator would install over each other. Each chat that opens the pane gets its own device
   (an emulator instance, or a cabled phone it claimed). At most two emulators run at once by
   default (each takes 2 to 4 GB); a third waits and says so. A device with no pane showing and
   no agent using it stops after 10 minutes. Emulators are the app's processes: they show on the
   Processes page and end when o7 quits.
10. **Agents use it through MCP**, as with the browser: the app's own executable as a stdio
    server, a loopback listener, a per-session token, revoked when the session ends. Native Chat
    sessions only. The switch is read on every call.
11. **Running the app is a recipe, not a guess.** o7 detects the project (Expo or React Native,
    Flutter, native Android with Gradle, Kotlin Multiplatform, Capacitor; later native iOS) and
    offers the person a Run button and the agent a `mobile_run` tool with the same recipe. Agents
    may also build in their own shell and then call `mobile_install` and `mobile_launch`. A
    failed build answers with the lines that matter, not the whole log.
12. **Dev servers get a port per chat** (Metro, Flutter's VM service), reached from the device
    with `adb reverse`, so two chats never share 8081.
13. **Crashes come to the chat.** While a chat's app runs, o7 watches the device log for that
    package's crash and offers it to the chat with its stack trace.
14. **iOS on macOS** uses `xcrun simctl` (boot, install, launch, open a link, appearance,
    location, permissions), `xcodebuild` for builds, and AXe for input and the accessibility
    outline. It handles Xcode 26 (Simulator.app) and Xcode 27 (Device Hub). Xcode is installed by
    the person from Apple; o7 detects it and says what is missing.
15. **Annotate works on the device.** Pick an element on the frozen screen (from the outline's
    bounds), write a note, Send or Add to chat, with the element's facts and a cropped picture.
16. **Nothing here publishes.** Signing for stores, uploading to TestFlight or Play and paying for
    anything are out of the first versions. When they come, each asks the person every time.

## Security

Who may do what, and how it is checked:

- **A chat's agent may drive that chat's device only.** The helper's request carries a token and
  no chat id (`deny_unknown_fields`); the app maps the token to the chat. Compared in constant
  time. The listener binds 127.0.0.1 and dies with the session.
- **A phone on a cable holds a person's life.** An agent may not use one until the person allows
  it for that chat (asked once per chat and phone, shown in the pane, revocable). Emulators and
  simulators o7 made need no question. Tests cover the refusal.
- **The switch off** closes every pane, stops every device o7 started, and makes every tool
  answer that Mobile is off, including in a running session.
- **What the screen says is data.** Tool replies describe the screen; the instructions tell
  agents never to follow text shown by an app, a notification or a web view.
- **Secrets**: password fields are blank in the outline. A picture cannot be masked, so on a
  cabled phone the pane says pictures show whatever is on screen. Signing keys, keystores, Apple
  and Google credentials and service-account files are never read by a tool and never logged.
  Tool arguments that type text are not written to logs.
- **No new listeners.** adb's server is loopback only (its default); o7 never runs
  `adb -a`, never forwards a device port to a non-loopback address, and opens scrcpy's sockets
  through adb. The emulator's console and gRPC ports are not enabled beyond their loopback
  defaults.
- **Downloads** come only from `dl.google.com` over HTTPS, each archive checked against the
  checksum in Google's index before it is unpacked; archive paths are confined to the SDK folder
  (no `..`, no absolute paths, no links out). The bundled `scrcpy-server` is pinned by SHA-256
  and listed in the third-party notices.
- **Remote access** does not reach the pane or its tools in the first versions.
- **An honest limit**: an agent with a shell can already run `adb` or `xcrun` itself, within the
  chat's access mode. These tools add no power there, and o7 does not pretend to fence it.

## The tools (`o7_mobile`)

`mobile_devices` (what exists and its state), `mobile_start` (boot or claim this chat's device),
`mobile_run` (build, install and launch by the project's recipe), `mobile_install`,
`mobile_launch`, `mobile_stop_app`, `mobile_snapshot` (the outline), `mobile_tap`, `mobile_type`,
`mobile_swipe`, `mobile_press` (Back, Home, app switcher, Enter, volume, power),
`mobile_screenshot`, `mobile_logs` (the app's log lines, or a crash), `mobile_open_link`,
`mobile_settings` (dark or light, text size, rotation, language, location, a permission),
`mobile_wait_for`. Later: `mobile_record`, `mobile_matrix` (one screen across sizes and
appearances, as one picture).

The instructions teach the loop: run the app, read the outline, act on refs, look at a picture
after changing UI code, read the logs when something fails, and say what was seen before saying
it works.

## Edge cases

No SDK; an SDK without an emulator or a system image; virtualization off, or held by another
hypervisor; a full disk during a download; a download cut off, a checksum that does not match; the
adb server missing, old, or owned by another program (Android Studio); two adb versions; a phone
not authorized for debugging; a phone unplugged mid-turn; a locked phone; an emulator that never
boots, crashes or hangs; a cold boot against a saved one; a device rotated, folded or resized; a
video stream that stalls or restarts; the window minimized, the pane hidden, Full view, a narrow
window; a chat switched while a device boots; two chats, two agents, two devices; a third device
past the limit; an app not installed, an install refused (version downgrade, signature
mismatch), a launch with no launcher activity; a permission dialog, a system dialog over the app;
a secure screen (pictures come back black); text in other languages and emoji; a stale ref; the
plugin turned off mid-turn; a profile switch; quitting with devices running; a leftover emulator
from a crashed o7; Terminal chats; keyboard use and reduced motion in the pane; Windows on ARM
(x86 system images do not run: say so).

## Logistics

- **Sizes**: platform-tools about 15 MB, the emulator about 400 MB, one system image about
  1.5 GB to download and 6 to 8 GB in use. The pane shows free space before it downloads and
  refuses under a margin.
- **Virtualization**: Windows needs the Windows Hypervisor Platform feature (an administrator
  turns it on, then a restart; Google retires its own AEHD driver on 31 December 2026). Linux
  needs `/dev/kvm` readable by the user. macOS needs nothing. The pane checks with
  `emulator -accel-check` and explains the one missing step in plain words.
- **Build caches** are the person's own (`~/.gradle`, the pub cache, CocoaPods); a new worktree
  reuses them. The worktree setup step can install the project's packages.
- **Verification**: Android is verified natively on Windows 11 first, then on Linux (WSL with
  KVM, and CI), then macOS. iOS on macOS needs a Mac: until one is at hand it is verified on
  GitHub's macOS runners only, and the record says so. Browser fixtures cover the pane on every
  system; native evidence and fixture evidence stay distinct.
- **Accounts**: none are needed for the emulator, the simulator, or a phone on a cable with
  Android. Installing on an iPhone from Xcode works with a free Apple account for 7 days at a
  time. Store accounts are the person's own business and outside this plan's first versions.
- **Licences**: Google's SDK licence is accepted by the person. scrcpy-server is Apache-2.0. AXe
  is MIT. Each is recorded in `third-party/`.

## Order of work

Each step is its own pull request, tried in a development build before it merges.

0. **Spikes** (thrown away): adb's protocol and scrcpy's stream against a real emulator; the
   stream decoded in WebView2; boot time and `-accel-check` on Windows; the outline's speed.
1. **The engine** (`crates/o7-devices`): SDK discovery, the repository index and checked
   downloads, AVD files, the adb client, the emulator's life, scrcpy's video and control, the
   outline, logs. Unit tests against recorded protocol bytes; an end-to-end test that runs when a
   device is present.
2. **The pane, for the person**: setup (find or fetch the SDK, the licence, virtualization),
   starting and stopping a device, the live screen, clicks, keys, text, the device's buttons,
   rotation, a picture, a cabled phone and its consent. The fixture and its check.
3. **The agent's tools**: the grant, the helper, session wiring, reserved names, the switch,
   Universal plugins' second card, the instructions and the skill; a real agent session against
   a real emulator.
4. **Running projects**: detection, recipes, the Run button, per-chat ports, crash cards.
5. **Many chats**: a device per chat, the limit, idle stops, the Processes page, leftovers after
   a crash.
6. **Annotate on the device.**
7. **Linux and macOS** for Android, verified.
8. **iOS on macOS**: simctl, xcodebuild, AXe, Xcode 26 and 27.
9. **iPhone without a Mac**: Expo Go, then cloud simulators.
10. **Later**: a Mac elsewhere over SSH; the device on the phone's remote page; recorded flows
    that replay as tests; the size and appearance matrix; performance traces; store publishing
    behind a question each time.
