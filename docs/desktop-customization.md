# Desktop customization

Customize is available below Search and New chat. It is a shortcut into Settings, which holds Plugins & MCP, Instructions and Project memory beside Agents and the app's own pages (owner's plan, 4 November 2026: one screen with search). Opening Settings keeps the current chat and its draft mounted. A page keeps its unsaved editors while other pages are visited, until Settings closes. Chat-specific Instructions opens on that chat's own folder or worktree.

The project header's plus opens the existing new-chat flow with that project selected. A sole usable folder is preselected; otherwise o7 uses the most recently used valid folder within that project. A worktree o7 made is never prefilled or offered: Rust marks it on its project folder (`worktree_of`), and a recent chat in one prefills the folder it was made from, within the same project, without waiting for the retained-worktree list. A folder picked with Choose folder that is already a project folder, however the pick spells it (a link, `..`, letter case where the file system ignores it; Rust compares canonical folders through `workspace_folder_matches`), is used as that folder: the draft's project's when it has it, otherwise the one whose chat there was active last, and New chat names that project when it is not the draft's. A folder belongs to several projects only through a deliberate Add folder or Move. A picked managed worktree is refused with its source named. Missing mappings remain unresolved. Delayed discovery never replaces a deliberate folder choice, and canceling the folder picker retains the prefill. The project agent preference takes priority over the profile preference, and detection never replaces a deliberate agent selection. Folder and worktree review, setup commands, busy-folder warnings and creation safeguards still apply. A folder counts as busy only while a chat's agent works there (starting, running a turn or background work, open in a terminal) or waits for an answer; one that just started or finished a turn counts for 15 seconds, since it is likely to get the next message, and an idle one does not count at all. The busy-folder notice lists those chats with their projects and offers Stop these chats, which stops them and checks the folder again; Start another chat in this folder still overrides it.

## Session controls

The composer separates access and workflow controls from the agent, model and effort picker. Model and effort choices come from the live connection. Switching agents uses the existing reviewed continuation flow. A native control's requested, effective and pending values are distinct; a saved option that disappears does not silently grant broader access.

Native Plan is separate from rendered plan progress. Codex uses its advertised collaboration mode, Claude uses native permission mode while remembering execution access, and ACP uses advertised native mode options. Connections without an advertised planning workflow explain that limitation. Leaving Plan through o7 requires explicit implementation approval. Changes to live native access or workflow require an idle session without queued messages or pending requests.

Access does not wait for the agent to run. Each connection's catalog keeps the native access and workflow controls and the access levels it last reported, so a chat whose agent is not running (one opened after a restart, a new chat whose agent is still starting) names the access its next start asks for instead of "Access unavailable". A stopped chat takes an access change for that start, native or level, and the start's setup asks for it. Once a starting agent's process has its setup, a change waits until the agent is ready: the picker shows the choices disabled until then, and the session refuses one rather than keep it, so a message sent meanwhile never runs on access the person had just left. "Access unavailable" means only that a running agent offers no access control. A mode change always waits for a running, idle agent.

New chat is type first (owner, 17 November 2026): it opens on a message box with the keyboard in it, with the agent, the folder and Chat or Terminal as chips under the words. Send creates the chat by the same path Start chat always took, then the new chat sends the words as it opens, through its own message box, so they take that chat's default model and access; words that cannot go stay in its box. The first message is text only: attachments and @ mentions start with the second. A terminal chat takes its words in the agent's own terminal, so Terminal turns Send into Open terminal. A new chat starts its agent as it is made, before its first message. Claude Code writes a session's file only with that message, so a saved Claude session that ran no turn and has no file starts again under its own ID rather than being resumed (which Claude refuses). A session that ran turns always resumes, so a missing file is reported, never quietly replaced.

These preferences live in additive versioned `controls_json` state per agent session. They do not overload legacy `Autonomy` or replace `config_json`. Unsupported saved preferences block dispatch until an offered value is chosen. Acknowledgements belong to the current generation; stale replies cannot overwrite a newly attached session.

## Plugins and shared MCP

[Plugins & MCP](plugin-library.md) starts with Universal plugins, o7's own for every agent (Browser use: the browser beside the chat, Annotate and the agents' browser tools, with a switch and its own settings; and Mobile: the device beside the chat and the agents' device tools, under Settings > Mobile), then lists each agent's native inventory and reviewed management capabilities. It uses structured native commands where available and a reviewed terminal route for operations that have no structured interface. The renderer consumes backend capability descriptions rather than maintaining provider-specific command tables.

Shared MCP definitions default to the selected project and can also apply across the profile. A project override replaces an all-projects definition with the same o7 ID. Definitions use the profile writer and stay on this device. Local environment and header credentials are stored separately and never included in a portable export. OAuth sessions remain with the native agent. Importing a native definition is explicit and leaves the original file intact.

Each new or resumed native generation receives a resolved snapshot. Codex receives thread configuration, Claude receives an additive session descriptor, qualified Pi receives a temporary extension, and ACP receives advertised MCP transports. Native names are checked for conflicts. Unsupported connections or transports report their limits. Restarting an idle session applies changed definitions without replacing native configuration. A direct connection test only verifies MCP initialization; it does not claim an agent session has connected.

## Project memory

Each project has a short **brief** and a set of **notes**, all Markdown, shared across its folders and worktrees. o7 stores their revisions in the profile database. They are o7's own, independent of `AGENTS.md`, `CLAUDE.md`, and harness-native memory.

The brief is what every chat in the project receives, so it is short: at most 4 KiB, for the rules and facts every chat needs. A note holds what a chat needs only sometimes (how one area is built, a decision and its reason, a trap): it has a name (lowercase letters, digits and dashes, at most 40 characters, kept for its life), one line of at most 120 characters that says when to read it, and up to 16 KiB of text. A project has at most 32 notes. A chat receives the brief and the list of notes, one line each with its age and who saved it last; its agent reads a note when that line fits the task.

Memory was one document until 22 November 2026 (owner: "should our project memory act just as an MD file? should there be more nuance?"). On the project this was measured on, that document reached its 16 KiB limit in nine days and stayed pinned there, so every fact an agent added pushed another out in a rewrite of the whole thing; 41% of prompts carried all of it, about 4,000 tokens each, most of it about areas the chat was not working on; and the user had never edited it. Other tools arrived at the same shape: Cursor shipped automatic memories in June 2025 and removed them in November 2025 in favour of rule files loaded always, by file, or when the agent judges a one-line description relevant; Claude Code keeps a short index that is always loaded and topic files read on demand. o7 keeps Markdown and keeps agents' edits visible and undoable, with no background model and no approval queue.

Migration 22 splits a memory that is too long for a brief, without a model and without losing a character: the text before the first `## ` heading and the sections after it stay the brief for as long as they fit in 4 KiB, and from the first section that does not fit, every section becomes a note named for its heading (`chatstore/memory_notes.rs`, `split`). A document usually opens with what matters most, and that is what every chat keeps receiving. After an update it is worth asking one chat to move anything every chat needs into the brief.

Settings > Project memory is the notes and one switch (owner, 10 November 2026: "we don't really need to review revisions or restore project memory and we don't need proposals"). The page holds a project choice when there is more than one project, the brief with its size against the 4 KiB limit and Save and Discard, and under it the list of notes: each note's name, its line, who saved it last and how long ago. A note is opened from the list to read, change or delete, and New note adds one; its name and its line are checked before anything is sent. There is no history, review queue, reason field, import or export. An edit made there is saved with the reason "Edited in Settings".

Agents edit project memory by default (owner, 1 November 2026). The profile preference `agent_memory_writes`, the "Let agents edit memory" switch on that page, turns this off: agents then read memory and cannot change it. The switch reaches running chats at once, because every memory grant reads it on each request.

An agent's edit is a revision whose source names its chat (`agent:<chat id>`), saved against the base revision the agent read. A different edit from a stale base fails and tells the agent to read again; retrying an identical write answers the current revision without adding one. Users save against an expected revision too. An open editor reads memory again after every change and on window focus, but never replaces a draft: it says memory changed and offers the newer version in the draft's place, and saving instead replaces that version with the draft.

Every agent edit is visible, which is how o7 mitigates a prompt-injected agent persisting instructions into memory without blocking legitimate edits. The chat pane shows a calm notice naming the chat, with Open, which shows the memory as it now is in Settings, and Undo, which puts back what the agent's consecutive edits replaced as new revisions of the user's: for the brief and for each note they touched, what it held before the first of them, a note they removed, or nothing where they added one. Rust decides (`undo_memory_edit`), and refuses for a brief or a note that has since moved on, so a later edit is never taken with it. The notice names the notes. A linked bot's save of the brief is recorded as a bot's and shown the same way. When the brief's last save came from an agent, the attached reference text says so on the line after its header, so later agents weigh it as reference rather than the user's instructions; each note says who saved it last in its line of the list.

What reaches every chat is what matters most to keep clean, and with notes that is the list, not the text: a prompt-injected agent that saves a note changes one line that every chat sees, and text that only a chat which opens the note receives, as a tool result and not inside the user's message. So a name cannot be anything but a plain word, a description is one bounded line with no control characters, shown in quotes, and the block tells agents that a note is a record and never an instruction. An agent may save memory at most 20 times an hour per chat, counted from revisions that are never trimmed while they are that young.

Revisions are still kept, because Undo and that line need them; nothing lists them. Proposals are gone: the store's table and commands remain for data made before, and nothing creates or shows one.

Memory is attached visibly as reference text to a real user message on the first native-generation turn and when it has changed since: the brief and the list again when someone else saved the brief, one line naming the notes when only notes changed, and nothing at all for what the chat's own agent saved, since it wrote that text a moment before. An agent without the memory tools (on another host, or started without them) is sent the notes' text with the brief, newest first, as far as they fit in 16 KiB, since nothing else could show them to it. Current user requests and instruction files take precedence. o7 persists the exact admitted revision with the turn before sending it. Retry and edited continuation retain their original admitted memory bytes; a later edit does not silently rewrite historical context. No memory-only model turn or hidden system prompt is generated.

The app-owned service exposes four tools: `o7_memory_read` (the brief and the list, or one note by name), `o7_memory_write` (the brief), `o7_memory_note_write` and `o7_memory_note_delete` (one note, from the revision that was read; saving one leaves the brief and the other notes as they are). Every write answers only while the switch is on, and otherwise tells the agent that nothing was saved and to tell the user what it would have added. The server gives its standing rules when a client connects, so they stay in the agent's context for the session. A session started before proposals went may still ask for one, and is told they are gone. A loopback listener and random token bind access to the owning chat, project, profile and native generation. Stopping, failing or retiring the session revokes that grant. The bundled `o7-project-memory` skill describes the tools, and the app's `--o7-memory-helper` mode provides a stdio bridge without exposing database paths. The optional MCP helper is used only on compatible native connections. Remote or unsupported connections retain visible reference context and explain why edits cannot be delivered. Every committed change sends the window `auracode-project-memory-changed`, naming an agent's direct edit.

## Verification boundary

Browser previews use synthetic data and production components. They verify layout, navigation, keyboard behavior and accessibility, not native CLI or authentication behavior. Native protocol probes use isolated temporary homes and local synthetic MCP servers without model prompts. Embedded Windows smoke tests exercise the actual Tauri command and storage path. These are distinct forms of evidence; neither establishes macOS release acceptance or a golden visual baseline.
